# Romby (Next.js): meeting-room booking

The Next.js version of [`demo1`](../demo1). Same app, same UI components, same exercises and same hidden bug. Here the frontend and the backend live in **one** Next.js app: React components in `client/`, API route handlers in `app/api/`, and the backend layers in `server/`. Use it for participants who work full-stack in TypeScript.

Romby lists meeting rooms and shows a weekly calendar for the selected room. You can add bookings and delete them. A room cannot be double-booked.

| Part   | Stack                                                                                         |
|--------|-----------------------------------------------------------------------------------------------|
| App    | Next.js 16 (App Router, Turbopack), React 19, TypeScript 7                                     |
| Data   | Node's built-in `node:sqlite`, in memory. No ORM, no native npm modules                        |
| Tests  | Vitest, calling route handlers directly                                                        |

There is no Docker, no external database and no cloud API. The database is created and seeded in `server/seed.ts` the first time it's used, and the seed bookings always land in the current week. Restart `npm run dev` to get fresh data.

```
app/
  layout.tsx, page.tsx, globals.css
  api/rooms/route.ts             GET /api/rooms
  api/rooms/[id]/route.ts        GET /api/rooms/:id
  api/bookings/route.ts          GET /api/bookings?roomId=, POST /api/bookings
  api/bookings/[id]/route.ts     DELETE /api/bookings/:id
client/                          the UI, copied from demo1/frontend/src (only adds 'use client' to App.tsx)
  App.tsx, api.ts, hooks.ts
  components/  RoomList, WeekCalendar, BookingForm
server/
  db.ts, seed.ts, errors.ts
  rooms/     room, roomRepository
  bookings/  booking (+ overlaps()), bookingDto, bookingRepository, bookingService
tests/
  rooms.test.ts                  the only test, on purpose
AGENTS.md                        generated by Next.js; tells coding agents to read the bundled docs
```

### How it maps to the Kotlin version

| Spring Boot (`demo1`)                        | Next.js (`demo1-nextjs`)                                        |
|----------------------------------------------|-----------------------------------------------------------------|
| `@RestController` + `@GetMapping`            | `app/api/**/route.ts` exporting `GET`, `POST`, `DELETE`          |
| `@Service` / repository beans                | plain modules exporting objects (`bookingService`, `bookingRepository`) |
| `Mono<T>` / `Flux<T>` (Reactor)              | synchronous calls: `node:sqlite` doesn't return promises         |
| R2DBC repository with derived queries        | hand-written SQL in `bookingRepository`                          |
| `ResponseStatusException`                    | `ApiError` + `handleErrors()` that returns `{ status, message }` |
| H2 in-memory + `schema.sql` / `data.sql`     | `node:sqlite` in memory + `SCHEMA` in `db.ts` + `seed.ts`        |
| `LocalDateTime` + Jackson                    | `LocalDateTime` type alias for `string` + `parseBookingDto()`    |
| `WebTestClient`                              | Vitest, calling the exported `GET`/`POST` functions              |
| separate Vite frontend with an `/api` proxy  | the same React components, served by the same app                |

## Prerequisites

- **Node.js >= 24** (with npm). `node:sqlite` is built in from Node 22.13, so there is nothing native to compile.

## Running

```bash
npm install
npm run dev
```

Open <http://localhost:3000>. The API is on the same port: try `curl localhost:3000/api/rooms`.

In IntelliJ / WebStorm / VS Code, open this folder and run the `dev` npm script.

Run the tests with `npm test`. `npm run build` also type-checks the whole project.

### Preparing for offline use (do this before the workshop)

```bash
npm ci          # installs exactly what package-lock.json specifies
npm run build   # confirms everything compiles without network
```

The layout deliberately doesn't use `next/font/google`, which downloads fonts at build time.

Also download your local model (for example a `qwen2.5-coder-7b-instruct.Q4_K_M.gguf` or a `-4bit-mlx` variant) and test it once with the IDE plugin while you still have network.

## Exercise 1: Inline completion

The goal is to write code while the local model suggests the next lines. Start typing and accept suggestions with Tab. Watch how well the model picks up patterns from the surrounding code.

| Where | What to write | Pattern to imitate |
|---|---|---|
| `server/bookings/bookingDto.ts` | `export const toRow = (dto: BookingDto): Omit<Booking, 'id'> => ({ ... })`, then use it in `bookingService.create` | `toDto` directly above |
| `server/bookings/bookingRepository.ts` | more queries, e.g. `findByRoomIdAndStartBetween: (roomId: number, from: LocalDateTime, to: LocalDateTime) => ...` or `findByBookedBy` | `findByRoomId` |
| `client/hooks.ts` | `export function useBookings(roomId: number \| null)` returning `{ bookings, error, reload }`, then replace the inline `useEffect` in `App.tsx` | `useRooms` in the same file |
| `app/api/rooms/available/route.ts` (new file) | `GET /api/rooms/available?minCapacity=6` | `app/api/rooms/route.ts` and `api/bookings/route.ts` |

Tips:
- Type a comment first, such as `// returns all bookings for a room within a week`, then start the signature.
- The last row starts from an empty file. How much does the model infer from the file path alone, compared with having a similar file open in another tab?
- Compare small (1.5B to 3B) models with larger (7B+) ones. Small models are fast but drift more.

## Exercise 2: Chat on selected code

Select the code, open the plugin chat, and use prompts like these:

1. **Explain the request flow.** Select `app/api/bookings/route.ts` and `bookingService.create`.
   > Explain step by step what happens when the browser POSTs a booking. Everything in `create` is synchronous. What does that mean for a Node server handling many requests at once? Can two requests double-book the same slot?

   (Short answer: not today, because nothing awaits between the conflict check and the insert, so no other request can run in between. It becomes a race as soon as the repository turns async, for example when moving to Postgres. Did the model spot that?)

2. **Generate tests for a pure function.** Select `overlaps()` in `server/bookings/booking.ts`.
   > Write Vitest tests for this function. Cover back-to-back bookings, zero-length intervals, one interval fully containing the other, and identical intervals. Use `test.each` where it fits.

   Then check the result: is the zero-length case actually correct? And what does the string comparison assume about its input?

3. **Refactor clunky code.** Select `bookingService.validate`.
   > Refactor this nested-if validation into idiomatic TypeScript using guard clauses. Return a discriminated union, `{ ok: true } | { ok: false; reason: string }`, and update the caller.

4. **Write route handler tests.** Select `tests/rooms.test.ts` and `app/api/bookings/route.ts`.
   > Using this test as a pattern, write tests for POST /api/bookings: a valid booking returns 201, an overlapping booking returns 409, and a blank title returns 400. Call the exported `POST` function directly with a `NextRequest`.

   Follow-up: the database is module state shared by every test in the file. Do the generated tests depend on each other's bookings?

## Exercise 3: Agentic coding (a bug across layers)

Give the agent (Continue/Cline/Aider/etc. in agent mode, using a local model) a bug report written the way a user would write it:

> Users report that bookings show up at the wrong time. If I book Fjorden on Wednesday from 09:00 to 10:00, the calendar shows it at 07:00–08:00. Also, I can't book Monday 11:00–12:00 even though the room is free then ("Room is already booked in that period"), but I *can* book on top of the 09:00 sprint planning. Find the cause and fix it. The UI is in `client/`, the API in `app/api/` and `server/`.

How to reproduce it yourself: run `npm run dev`, select Fjorden, and book Wednesday 09:00–10:00 in the form.

Things to discuss afterwards:
- Did the agent read across files (React form to DTO to service to calendar), or did it patch only the symptom (for example adding 2 hours in the calendar)?
- Did it notice that the size of the shift changes with daylight saving time (2 hours in summer, 1 in winter in Norway)?
- Here the browser and the server run on the same laptop, in the same time zone. Did the agent "fix" it by converting with `new Date(...)` on the server? That works on your laptop and breaks as soon as the server runs in UTC, which is the default on most hosting.
- Did the agent read `AGENTS.md`? Did it help or just cost context?
- How many tool calls and how much context did the local model need, compared with a cloud model?

### Symptom

In a browser running in Europe/Oslo, a booking for 09:00–10:00 is stored and shown as 07:00–08:00 (summer time, UTC+2) or 08:00–09:00 (winter time, UTC+1). The conflict check compares these shifted times against seed data stored in local time, so real conflicts are missed and false conflicts appear.

### Root cause (several layers, each looking reasonable on its own)

1. **`client/components/BookingForm.tsx`**: `<input type="datetime-local">` gives `"2026-10-14T09:00"` (local, no zone). The form sends `new Date(start).toISOString()`, which converts to UTC: `"2026-10-14T07:00:00.000Z"`.
2. **`server/bookings/bookingDto.ts`**: `toLocalDateTime()` "normalises" the value by keeping the first 19 characters. That silently cuts off `.000Z`, leaving `"2026-10-14T07:00:00"`. No error, no warning. The examples in its comment never show a zone, so nobody thought about one.
3. **`server/bookings/booking.ts` / `overlaps()`**: compares `"…T07:00:00"` with the seed data, which is stored as local wall-clock time (`"…T09:00:00"`). The comparison is apples against oranges.
4. **`client/components/WeekCalendar.tsx`**: `new Date("2026-10-14T07:00:00")`. A string without a zone is parsed as *local* time, so the shifted value is displayed as 07:00.

Every layer does something defensible. The bug lives in the contract between them: is a timestamp "wall-clock time in the office" or "an instant in UTC"? Sharing one codebase doesn't help here. `LocalDateTime` is just an alias for `string`, so the compiler can't tell the two apart.

### Reference fix

A meeting room is in one physical building, so the booking is a **wall-clock time**. The fix is to stop converting to UTC in the form:

```diff
 // client/components/BookingForm.tsx
       const created = await createBooking({
         roomId,
         title,
         bookedBy,
-        start: new Date(start).toISOString(),
-        end: new Date(end).toISOString(),
+        // datetime-local is already local wall-clock time ("2026-10-14T09:00"),
+        // which is exactly what the server's LocalDateTime expects.
+        start,
+        end,
       })
```

Verify by booking 09:00–10:00 again: the calendar now shows 09:00, Monday 11:00–12:00 is allowed, and Monday 09:30–10:30 is rejected with 409.

**Alternative:** if the rooms were in different time zones, you'd go the other way: store instants (UTC ISO strings with `Z`) everywhere, including the seed data, and format to the room's local time only in `WeekCalendar`. That touches more files, which makes it a good follow-up prompt for the agent.

**Stretch goal:** ask the agent to make `toLocalDateTime()` *reject* strings that carry a zone (`Z` or `+02:00`) with a 400, instead of cutting them off, and to add a regression test that posts a `...Z` timestamp. Then discuss whether a branded type (`string & { __brand: 'LocalDateTime' }`) or the `Temporal.PlainDateTime` API would have caught this at compile time.
